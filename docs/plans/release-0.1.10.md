# After 0.1.9: what the outside reviews turned up

Three reviews of `docs/SPEC.md` and of the npm README came in on 2026-11-23. This file sorts their points: what is already
done, what is planned and in which order, and what was checked and dropped. Each planned item is "measure first" where it
claims a gain: keep it only if the number holds, and results stay bit-identical (`docs/SPEC.md`, section 3).

## Planned, in this order

### 1. Hardening (next)

1. **One implementation of insights and what-if.** `packages/wuica/lib/{insights,whatif}.js` re-implement
   `web/js/{bound,whatif}.js`; agreement is tested on the built-in examples only. Make them one file each, shared by the
   copy mechanism the other shared files use, and let `packages/wuica/build.sh` refresh the copies (the test stays as the
   check).
2. **Type checking without a build step**: `tsc --noEmit --checkJs` over the page, the package and the server in CI
   (TypeScript as a development dependency of the repository only; the package keeps no runtime dependency), and
   `index.d.ts` checked against the library for the first time.
3. **CI**: a Node 20 job for the package tests and a CLI smoke test (`engines.node` says `>=20`); wall-clock bounds in the
   browser suites as warnings on CI where a deterministic budget (draw calls, DOM nodes, allocations) can replace them.
4. **An accuracy gate in CI**: the held-out sets and the dogfood loops as `(machine code, measured cycles)` per CPU in the
   CI data asset, scored by a native test that fails when the share within 10 % or the MAPE of a prototype model drops.
5. **Exactness tests the corpus does not give**: the rounding helper against Python's `round(x, 2)` for all `k / n`,
   `1 ≤ n ≤ 1000` (expected values generated by Python, kept as a fixture); an audit of integer widths against Python's
   unbounded `int` (`minIterations × instructions`, cycle counts); the lookup-only maps of `fasthash.rs` as a type without
   `iter`/`keys`/`into_iter`, so the rule is checked by the compiler.
6. **A differential fuzzer against the reference**, run before a release on the machine that has the reference: random
   valid blocks with pairwise option combinations (`alignmentOffset` × `initPolicy` × `simpleFrontEnd` × `noMicroFusion`
   × `noMacroFusion` × extreme `minIterations`/`minCycles`), compared field by field.
7. **A work budget before the simulation**: a block whose expanded uop count is far beyond anything useful (`wbinvd`)
   fails at once with result code 3 and a reason, instead of running for minutes or exhausting memory. No change for any
   block the reference handles in reasonable time; record the bound in `docs/DEVIATIONS.md`.
8. **Releases**: one script that checks the version everywhere (including `Cargo.toml`), and a smoke test of the live site
   and API after a deploy; a tag-triggered workflow only once publishing credentials are set up for it.

### 2. Payload and start-up (as the audit's numbers allow)

1. Serve the precompressed brotli files (first visit 2.19 MB as served against 1.64 MB at brotli q11).
2. The default first visit without the assembler: ship the first example's machine code, fetch the assembler in the
   background or on the first edit.
3. Ship the analyzer without its name section; keep the unstripped module as a build artifact for profiling.
4. Tables keyed by the numeric XED iform, if that lets XED's iform string table leave the module without changing output.

### 3. Interfaces for agents

1. `wuica diff a.s b.s` and an MCP `diff_blocks` tool: throughput before and after, speed-up, per-element change, the
   change of bottleneck, limits and ports, in one call.
2. The source line on each entry of `instructions[]`, `chain[]` and `hot.instructions[]` (and `.loc` lines when present).
3. `otherLoops` in the analyze response whenever the text has more than one loop, and a `list_loops` MCP tool.
4. An alignment variant in what-if: minimum, median, maximum and the worst offset over the 64 offsets.
5. `what_if` in REST; the same option ranges in every interface, or the differences stated once.
6. Input straight from profiles: `objdump -dS` (keeping the interleaved source lines) and `perf annotate` output.
7. Left from the dogfood runs: an "aligned loads" what-if, work per iteration in the REST and MCP compare.

### 4. Later, and the owner's decisions

- A write-up of the accuracy method with live links, and a one-command measurement harness so others can run the held-out
  sets on their own CPUs.
- The provenance and terms of the instruction tables, stated in the repository.
- OSACA as a second in-browser tool, if it is light enough.

## Checked and dropped

| Point | Why |
|---|---|
| "Steady-state detection stores state snapshots" | The simulator keeps no history of states; `fasthash.rs` is a hasher for lookup maps |
| Size-optimized build, SIMD, `wasm-opt` for speed | Measured before: `build-wasm.sh` records 25 % slower, no gain, no gain |
| Ring buffers, dense arrays, port masks in the simulator | Done in the earlier speed rounds (`docs/SPEC.md`, section 8.1) |
| One LLVM module for the assembler and llvm-mca | The assembler is built assembler-only and is on every visitor's path; llvm-mca is loaded on demand |
| Heaviest-first job queue for compare | The threads already pull from one queue and a compare's jobs are the same size |
| A native Rust API server | Low traffic today, and the assembler is a WebAssembly module either way; revisit if load grows |
| On-demand table lookup (tables read in place, entries decoded on first use) | Built and measured (commit `1b014e2`, reverted by `a296b2c`): tables ready in 24 ms instead of 62 ms and 14 MB instead of 39 MB of module memory for all 15, but the tables grow 32 % as shipped (797 kB to 1,049 kB) and small blocks get 1.0 to 2.8 % slower on ZEN3 and ADL-P in the module |
