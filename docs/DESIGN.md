# wuica design

## Goal

uiCA's predictions, bit for bit, from a Rust core that runs natively and as WebAssembly in a browser.
"Bit for bit" means: for the same machine code and microarchitecture, the same throughput and the same detailed results
(port usage per instruction, bottlenecks, cycle-by-cycle events) as the Python reference.

## Reference

The reference ("oracle") is the Python uiCA of the fork [jtl06/uiCA](https://github.com/jtl06/uiCA), branch `perf`, commit
`8f24bd3` (improve-r4 `a5ef6c2` plus the determinism fix `9b69d9d`, which the port depends on: before it, the scheduler iterated
over a set of objects and results could differ between runs). All fixtures are exported from this commit.

Not ported:

- the `CLX_SimplePorts*` configurations (they use Python's `random.choice`; they are ablation variants of the uiCA paper);
- `-graph` and `-depGraph` output (plotly, graphviz);
- IACA markers (the input is the code to analyze);
- `convertXML.py` and `setup.sh`: the instruction tables are still generated by the Python tools and exported to JSON.

## Architecture

```
machine code ──► wuica-xed ──► DecodedInstr ──► wuica-core::instructions ──► Instr ──► wuica-core::sim ──► Result ──► JSON
                 (XED, C)       (= Python dict)   (= instructions.py)         │        (= uiCA.py)                 (= -json)
                                                        ▲                     │
                                  arch data (JSON) ─────┘       uarch config (= microArchConfigs.py)
```

- `crates/wuica-xed`: the pinned XED decoder plus a C shim that produces the same records as uiCA's Python `xed` module. Done.
- `crates/wuica-core`: no C, no I/O. Data model, instruction builder, simulator, bottleneck analysis, result serialization.
- `crates/wuica-cli`: native command-line tool, for comparing with the reference and for general use.
- `crates/wuica-wasm`: the WebAssembly interface (plain exports; JavaScript reads and writes the module's memory).
- `web/`: a static page.
- `tools/`: Python scripts that run against a uiCA checkout: data export and fixture export.

### Data layout in the simulator

The Python simulator is a web of small heap objects (uop → properties → instruction; uop → fused uop → laminated uop; renamed
operand → producing uop). The port uses flat arrays indexed by integer ids instead: one `Vec` per kind of entity (instruction
instances, laminated/fused/unfused uops, renamed operands, store-buffer entries), with `u32` indices where Python has references.
All entities of a simulation live until its end (the results need them), so nothing is ever freed individually.

## Fixtures: the three boundaries

Each stage is checked on its own, so that a difference is found where it is introduced. Corpus: 329 files (random loops, BHive
basic blocks, all zenbench microbenchmarks, blocks of 10/100/1000 instructions).

| Boundary | Fixture | Exported by | Checked by |
|---|---|---|---|
| decoder output | `fixtures/decode_fixtures.jsonl.gz` (file × XED chip: hex, list of dicts) | `tools/export_decode_fixtures.py` | `crates/wuica-xed/tests/fixtures.rs`, `tests-js/decode_fixtures.mjs` |
| instruction objects | `fixtures/generated/instr_fixtures.jsonl.gz` (8056 cases: file × configuration × options that affect them): every field of every `Instr` after `getInstructions`, `adjustLatenciesAndAddMergeUops` and `computeUopProperties`; the JSON form of `wuica_core::model::InstrList` | `tools/export_fixtures.py` | `crates/wuica-core/tests/model_fixtures.rs` (the model holds everything), builder test |
| simulation result | `fixtures/generated/sim_fixtures.jsonl.gz` (9899 cases: file × configuration, and 8 option variants for 24 files): throughput and the detailed text output; the `-json` output for 1119 cases | `tools/export_fixtures.py` | simulator test |

The fixtures in `fixtures/generated/` and the tables in `data/` are generated (they are large): run `tools/export_data.py` and
`tools/export_fixtures.py` against a uiCA installation. Four simulation cases have an `error` field: the reference itself raises
an exception there (two in the `-json` output for ADL-P/ICX, where a fractional throughput limit makes a cycle number a float; two
in stock uiCA for SNB/IVB).

Both sides always get the same raw bytes (the hex string in the fixture).

## Rules for an exact port

These are the places where a straightforward translation gives different results:

1. **Iteration order.** Python dicts iterate in insertion order, and the code relies on it (`portData`, `regOperands`, `rw`,
   `latencies`, the rename dictionaries). Use `Vec` of pairs or `IndexMap`; never iterate over a `HashMap`/`HashSet`.
   Python *sets* that are iterated must be given a defined order that matches the reference (after `9b69d9d`, the only such
   place, `pendingUops`, is sorted by uop index).
2. **Integer division and modulo.** `//` and `%` round toward negative infinity (`disp // 64` with a negative displacement);
   Rust's `/` and `%` truncate. Use `div_euclid`/`rem_euclid` (for positive divisors).
3. **`min`/`max`/`sorted`.** `min` and `max` return the *first* of equal elements; `sorted` is stable; `heapq` with `(idx, uop)`
   tuples orders by `idx`. Rust's `Iterator::max_by_key` returns the *last* maximum: write these out explicitly.
4. **Numbers.** Latencies and throughput limits can be fractions (`TP`, `blockedResources`): Python mixes `int` and `float`
   freely. Keep the order of floating-point operations, and use `f64` where the Python value can be a float. The final
   throughput is `round(x, 2)`: Python rounds half to even on the exact binary value; check against the fixtures.
5. **Strings as data.** Much logic tests substrings of names (`'MM' in reg`, `'MOV' in instrStr`, `'I64' in instrStr`).
   Port these tests literally first; replace them with enums only where the fixture tests cover the difference.
6. **Identity vs. equality.** Operands (`RegOperand('RAX')`) are compared and used as dict keys by *identity* in Python: two
   operands for the same register are different keys. Give operands ids; do not key by register name where Python keys by object.
7. **Known quirks are part of the reference.** For example, `getRegSize` (fixed in `a100889`) and the `% 16`/`% 32` block
   splitting. If something looks like a bug, port it as it is, and report it; fixes go into the Python reference first.

## Work packages

After the decoder, the port splits into pieces with fixture-defined boundaries:

1. **Data export and loader**: `tools/export_data.py` (per architecture: `instrData`, `attrData`, `perfData`, `uArchInfo`; the
   `MicroArchConfig` objects) and the Rust types and loader. The `lat` dictionaries have tuple keys; sets must be sorted.
2. **Instruction builder**: `instructions.py::getInstructions` and `xed.matchXMLAttributes`, plus
   `adjustLatenciesAndAddMergeUops` and `computeUopProperties` from `uiCA.py`. Checked at the second boundary.
3. **Simulator**: front end (predecoder, decoder, DSB, LSD, microcode sequencer, op cache), renamer, scheduler, reorder buffer,
   the main loop and the throughput computation. Tightly coupled: one piece of work. Checked at the third boundary.
4. **Results**: the uop table data, `-json` output, bottleneck analysis (`facile.py`'s limits and the latency graph).
5. **Front ends**: CLI, WebAssembly interface, web page.

Packages 1 and 2 define the input of 3; 4 and 5 only consume its output.

## Open questions

- **Input.** The first version takes machine code as hex. Assembly text would need an assembler in the browser.
- **uops.info data.** No license is stated for it. The tables are therefore generated locally and not committed; publishing a
  build that contains them (e.g. a hosted page) needs the authors' permission.
- **Size.** The WebAssembly module with XED is 3.4 MB (0.6 MB gzipped), before the simulator. The instruction tables are
  0.6–3.4 MB of Python source per architecture; they are loaded per architecture on demand.
